# Grammar Audit — 2026-07-05

Method: first-ERROR-per-file extraction (56 failing files), per-line standalone
bisection, minimal-snippet verification, top-level vs in-lambda A/B test.

## Headline finding

**The same expression parses at top level and FAILS inside `{ }`.**

| construct | top-level | in-lambda |
|---|---|---|
| `r:x,'y` | ok | **FAIL** |
| `r:neg[h](`a;x;y)` | ok | **FAIL** |
| `r:0b sv' x` | ok | **FAIL** |
| `r:2*/:(sin;cos)` | ok | **FAIL** |
| `r:(til x)_\:x` | ok | **FAIL** |
| `r:v where c>x:0 t\x` | ok | **FAIL** |

Minimal repro: `f:{x,'y}` → ERROR. `r:x,'y` → clean.

Lambda body reuses the same `_statement` rule, so this is NOT a forked rule.
It is the GLR conflict set + missing infix-derived-verb rule: at top level the
ambiguity happens to resolve to *a* tree; inside `{ }` the tighter follow-set
(`}` / `;`) kills the accidental parse. **Passing tests here are accidents of
GLR tie-breaking, not evidence the construct is supported.**

## Root causes (structural, not per-construct)

1. **No infix rule for adverb-derived verbs.** `x f'y`, `x vs/:y`, `p#'q`,
   `a,'b` — q's most common idiom. `binary` only accepts a bare operator token
   as its operator; `adverb_apply` is postfix-only. Everything that currently
   parses does so by GLR accident.

2. **External scanner state model cannot work.**
   - `prev_was_value` is only ever set by tokens the scanner itself lexes
     (NEG_NUMBER). Identifiers, numbers, `)`, `]` are lexed internally — the
     scanner never sees them, so `prev_was_value` is false in exactly the
     positions ADVERB_TOK needs it (scanner.c:215). ADVERB_TOK essentially
     never fires; all adverbs ride the in-grammar fallback glyph.
   - `depth` (scanner.c:18) is declared, never incremented — dead.
   - CRLF check `lookahead=='\n' && lookahead=='\r'` (scanner.c:234) always false.

3. **Expression zoo + 8 GLR conflict entries.** `binary`/`call`/`index`/
   `adverb_apply`/`_application` overlap; conflicts kept as "disambiguation
   hints". Result: which node shape you get for a given source string is
   unpredictable — directly hostile to the AST-extraction goal.

## Confirmed concrete gaps (minimal repros)

- `f:{x,'y}` — any derived verb infix inside lambda (majority of the 56 files)
- `r:g[a;b]'[c;d]` — adverb after bracket-call, then bracket args
- `f:{{cond}{body}/x}` — over applied to juxtaposed lambdas (while-loop idiom)
- `dmm2:{...}\:` — adverb directly on lambda
- `r:count$[c;a;b]` — builtin juxtaposed with cond (`system$[...]`, `getenv$[...]`)
- `v:$[c;value;] x` — trailing-elided cond branch then juxtaposed apply
- `$[c;[a:1;b:2];0]` — `[e1;e2]` bracket statement block
- `view::select from t where ...` — `::` view definition of qsql
- `a:{d+0^(x,1)r[7]d:dy[y]z}` — juxtaposition chains
- `noise:{[n] (-.5+n?1f)+n?-5 -4 -3}` — `(-.5...` neg-float opening a paren
- `k)...` lines — k-mode (2 files, low priority; treat as opaque token)

False positives in earlier bucket counts: prose after bare `\` (end-of-script)
parses fine; block comments fine; `\d .ns` fine; multi-line lambda per se fine.

## Verdict

Whack-a-mole on this architecture will not reach <2%. Each "fix" adds another
GLR conflict and shifts which accidental parse wins. Rebuild the expression
core on q/k's actual grammar model:

```
expr    := noun | verb expr | noun verb expr
verb    := op | derived
derived := (op | noun | derived) iterator      # iterators postfix, stack
noun    := literal | name | (expr) | {lambda} | noun[args] | noun iterator? noun
```

One uniform application rule, RTL via right recursion, iterators as first-class
postfix on ANY verb-ish thing. This deletes `binary`-vs-`adverb_apply`-vs-
`call` overlap and most conflict entries. Scanner keeps only what is genuinely
lexical: comments, system commands, EOS, vector whitespace, neg-number
(left-context via grammar structure, not `prev_was_value`).

Alternative considered: fork jshinonome/tree-sitter-q (used by vscode-q) and
add extraction-oriented node names. Viable fallback if rewrite stalls.
